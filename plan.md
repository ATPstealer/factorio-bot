# Factorio Bot — план

Цель: бот с нуля строит базу и запускает ракету (Factorio 2.0.77, base, без Space Age) без единого клика игрока.
Первая карта — фиксированный сид, кусаки выключены. Дальше — адаптация к любой карте.

---

## 0. Ключевые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Версия | Factorio 2.0.77, только `base` | ✅ утверждено. «Улететь» = запуск ракеты (победа в base). |
| Честность | ✅ **Действия — только ввод мыши/клавиатуры** в окно игрового клиента (эмуляция ввода ОС). Мод **ничего не меняет** в игре — только читает состояние. | Правила игры соблюдает сама игра (досягаемость, инвентарь, время крафта) — отдельная проверка правил не нужна. |
| Глаза | Lua-мод `botbridge` — **read-only** сенсоры, отдаёт JSON по RCON | Информация через мод разрешена, но ✅ **только то, что видит игрок**: открытые (charted) чанки, свои инвентарь/исследования, справочник прототипов. Неоткрытую карту не читаем и не генерируем. Скриншоты — только для калибровки/проверки GUI. |
| Руки | Go-бот шлёт ввод через **XTEST** (X11, сессия XFCE) в окно клиента | Реальные клики/клавиши, как у живого игрока. |
| Запуск игры | Headless-сервер (`--start-server`, RCON, свой `--config`/write-data) + **клиент** Steam, подключённый к нему | RCON есть только у сервера; клиент — тот, кем «играет» бот. |
| Изоляция ввода | Клиент запускается во вложенном X-дисплее (**Xephyr**), бот кликает только туда | Твоя мышь/клавиатура свободны; ты смотришь в окно Xephyr. |
| Строительство в поздней игре | Чертежи через GUI (импорт строки из буфера обмена) → призраки → строительные роботы | Как живой игрок. Цель — дойти до роботов как можно раньше. |

## 1. Архитектура

```
┌──── Factorio headless server ────┐        ┌──── Xephyr :1 ─────────────────────┐
│ mod "botbridge" (read-only)      │◄──────►│ Factorio client (игрок бота)       │
│  ├─ remote interface (запросы)   │  game  │   ▲ мышь/клавиатура (XTEST)         │
│  ├─ sensors (прототипы, карта,   │  net   └───┼────────────────────────────────┘
│  │   сущности, игрок, GUI-state) │            │
│  └─ event buffer                 │            │
└───────▲──────────────────────────┘            │
        │ RCON: remote.call("bot", ...) → json  │
┌───────┴────────────────────── bot (Go) ───────┴─────────────────────────────┐
│  rcon client → bridge API (только чтение)                                   │
│  input        (XTEST: мышь, клавиши, удержание, буфер обмена)               │
│  camera       (мир ↔ пиксели: позиция игрока, зум, разрешение, UI scale)    │
│  gui driver   (макросы: инвентарь, крафт, тех-дерево, окно сущности)        │
│  world model / knowledge / strategist / planner / layout                    │
│  executor     (примитив → ввод → проверка результата через сенсоры)         │
│  monitor / logs+replay                                                      │
└─────────────────────────────────────────────────────────────────────────────┘
```

Правило: в remote interface мода нет ни одного метода, меняющего игру. Бот по RCON вызывает только `remote.call("bot", ...)`, никаких произвольных `/c`.

Структура репо:
```
/mod/botbridge/          info.json, control.lua, sensors/*.lua
/cmd/bot/                main.go
/internal/rcon/          RCON-клиент
/internal/bridge/        API к моду (чтение)
/internal/input/         XTEST: мышь, клавиатура, буфер обмена
/internal/camera/        проекция мир ↔ экран
/internal/gui/           макросы работы с GUI игры
/internal/world/         модель мира
/internal/knowledge/     рецепты, техи, калькулятор
/internal/planner/       HTN, стек задач
/internal/layout/        шаблоны, размещение, A* для лент
/internal/executor/
/internal/monitor/
/scripts/                запуск сервера/Xephyr/клиента, генерация карты, установка мода
/blueprints/             шаблоны модулей (blueprint-string)
```

## 2. Стадии разработки

Каждая стадия — отдельный критерий готовности. Следующую не начинаем, пока не пройден критерий.
Критерий оформляется e2e-тестами `test/e2e/stageN_test.go`; `scripts/test.sh` гоняет все стадии — после каждой стадии проверяем, что предыдущие не сломаны.

### Стадия 0. Окружение
- Генерация карты: фиксированный сид, `map-gen-settings.json`: `enemy-base` frequency=0, утёсы выключены (`cliff_settings`).
- Headless-сервер: `--start-server bot.zip --rcon-port 27015 --rcon-password ... --server-settings ...` с `"auto_pause": false`, отдельный `--config` (свой write-data, иначе конфликт lock-файла с клиентом) и `--mod-directory`.
- Xephyr `:1` фиксированного разрешения (например 1920×1080), клиент Factorio запускается в нём, автоподключение `--mp-connect localhost`.
- Настройки клиента фиксированы: разрешение, UI scale 100%, оконный режим, раскладка клавиш по умолчанию (бот на неё опирается).
- Мод ставится в mods-dir сервера и клиента (симлинк).
- Пакеты: `xserver-xephyr`, `xdotool`/libXtst (для отладки), `xclip`.
- Go toolchain (сейчас `go` не в PATH).

**Готово, когда:** одна команда поднимает сервер + Xephyr + клиент, клиент в игре на карте без кусак.

### Стадия 1. Мост (глаза) и руки (ввод) — ✅ готово
- Мод: `remote.add_interface("bot", {call})`, ответ через `rcon.print(helpers.table_to_json(...))`. Только чтение.
- Go: RCON-клиент, `bridge.Call(method, args, &out)`. Пагинация не понадобилась: RCON отдаёт ≥2 МБ одним пакетом.
- Методы: `ping`, `tick`, `get_player` (позиция, зум, разрешение, инвентарь, quickbar, cursor, `opened`, крафт-очередь, reach, selected), `find_nearest`, `entity_at`.
- Event buffer: мод копит события, бот забирает `poll_events{after}`.
- Go-ввод через XTEST (xgb, без cgo) в `:1`: клавиши, текст, мышь, колесо. Буфер обмена — отложен до чертежей (стадия 9).
- Камера: проекция мир ↔ пиксели по позиции игрока и зуму. Зум не меняем (1.5 устраивает) — читаем из игры. Калибровка: наведение подтверждается `selected`.

**Готово, когда:** бот подходит клавишами WASD к точке, наводит курсор на дерево (`selected` подтверждает) и срубает его ПКМ.
Тесты: `test/e2e/stage1_test.go` (Walk ≤0.5 тайла, Mine + событие mined_entity, OnlyCharted).

### Стадия 2. Сенсоры (глаза) — ✅ готово
Всё — только по открытым (charted) чанкам: бот знает карту так, как её видит игрок.
- `dump_prototypes{kind}`: рецепты, предметы, сущности (размеры, коллизии, скорости, энергия, топливо), технологии (стоимость, зависимости, что открывают, **trigger** — в 2.0 часть тех открывается действием: `electronics` = скрафтить 10 медных пластин). Кэш `data/prototypes-<версия>.json`.
- `list_charted`, `scan_chunks{chunks}`: тайлы (суша / вода / мелководье / край), ресурсы с остатком, объекты (статус — для своих). Неоткрытый чанк → `charted=false`.
- `get_force` (исследования, доступные рецепты). Статистика производства убрана как неиспользуемая — вернуть в стадии 11 (мониторинг).
- Событие `chunk_charted`; `world.Sync` пересканирует новые чанки и чанки, затронутые событиями.
- Go: `internal/knowledge` (справочник), `internal/world` (модель: тайлы, ресурсы, объекты, коллизии, проходимость, месторождения, PNG).
- CLI: `bot map`, `bot patches`, `bot protos`, `bot force`.

**Готово, когда:** бот строит в памяти карту стартовой зоны (ресурсы, вода, препятствия) и выводит её отладочной картинкой (PNG).
Тесты: `test/e2e/stage2_test.go` (модель совпадает с игрой по руде/воде/деревьям; неоткрытое не сканируется — в Stage1 OnlyCharted).

### Стадия 3. Примитивы действий через ввод — ✅ готово
Принцип: где можно — хоткеи; мышью — наводить и кликать по миру; клики по интерфейсу — только в фиксированные, откалиброванные точки, каждый шаг подтверждается модом.

| Действие | Ввод |
|---|---|
| `WalkTo/WalkNear` | путь A* по модели мира (вода, коллизии объектов, без срезания углов), удержание WASD по точкам поворота, доводка у цели; застрял — перестроить путь |
| `Gather/Mine` | навести (selection_box, `selected`) → держать ПКМ; не копает — повторное нажатие |
| `Craft/CraftWait` | `E` → `Ctrl+F` → название → клик по ячейке рецепта (ячейка вычисляется как в интерфейсе: группа → подгруппа → order); ПКМ = 5 шт.; проверка — очередь + события `crafted_item`; промежуточные крафты игра ставит сама (`prerequisite`) |
| `Pick` | клавиша быстрой панели `1..0`; если предмета на панели нет — один клик по ячейке инвентаря + клик по свободному слоту панели (привязка), дальше всегда хоткей |
| `ClearCursor` | `Q` (только при занятой руке — иначе это пипетка) |
| `Place` | Pick → навести на центр площадки → ЛКМ → событие `built_entity`; `R` по постройке до нужного направления |
| `Insert` | Pick → навести → `Z` n раз (одно нажатие = один предмет) |
| `Take` | `Ctrl+ЛКМ` с пустой рукой |
| `Pickup` | удержание ПКМ на своей постройке |
| `research`, `set_recipe` | перенесены в стадию 7 (нужны лаборатории/сборщики) |

Найдено по ходу:
- нажатие короче ~30 мс игра может не заметить → `Tap` держит 50 мс; ввод доходит до сервера через 1–3 тика → проверки ждут задержку;
- `Esc` без открытого окна открывает меню игры (мод его не видит) → распознаём по пикселям кнопки Resume, `Clean()` закрывает;
- в 2.0 буры ставятся только на ресурсы;
- снимок экрана при сбое действия → `run/debug/`.

**Готово, когда:** сценарий «добыть 10 камня → скрафтить печь → поставить → закинуть уголь и руду → забрать пластины» проходит без ручного вмешательства.
Тесты: `test/e2e/stage3_test.go`, `stage3_complex_test.go` (Craft, PathAroundLake, FurnaceScenario, Guards, DrillOneOreTile, FurnaceHugsTree, DropAndCollectInOrder, SnailMaze).

### Стадия 4. Знания и калькулятор — ✅ готово
Чистая логика на Go поверх справочника из стадии 2 — без ввода, почти без игры. Пакет `internal/knowledge` (граф) + `internal/calc` (калькулятор).

**4.1. Граф рецептов и предметов**
- Предмет/жидкость → рецепты, которые его производят / потребляют; рецепт → категория → машины, которые его делают (crafting_categories) + руки персонажа (`crafting`).
- Сырьё: ресурсы (руды, нефть) и вода (offshore-pump), из прототипов ресурсов: mining_time, required_fluid (уран — серная кислота).
- Сущности-производители по ролям: сборщики, печи, химзавод, НПЗ, центрифуга, ракетная шахта; буры (mining_speed, resource_categories, область); лаборатории (researching_speed, lab_inputs); энергия: бойлер / паровой двигатель / помпа, солнце, аккумулятор; столбы (supply_area, wire_distance); ленты (скорость), инсертеры.
- Учитывать 2.0: часть техов открывается действием (trigger: craft-item / mine-entity / build-entity…), а не наукой — `automation-science-pack` = скрафтить лабораторию, `electronics` = 10 медных пластин.

**4.2. Доступность (с учётом силы игрока)**
- Из `get_force`: изученные техи, открытые рецепты. «Доступно сейчас» = рецепт открыт и есть машина его категории (или руки).
- Выбор машины по умолчанию — лучшая доступная (assembler 1→2→3, stone→steel→electric furnace, burner→electric drill); флаг принудительного выбора.

**4.3. Калькулятор скоростей** (`calc.Solve(цели, ограничения) → План`)
- Вход: цели «предмет: N/мин» (несколько сразу), набор доступных рецептов/машин.
- Расчёт по дереву: скорость рецепта = нужный выход / продукт за крафт; машин = скорость × energy / crafting_speed (дробно и с округлением вверх); входы — рекурсивно до сырья.
- Сырьё: руда/мин → число буров (mining_speed / mining_time ресурса), плавка → печи.
- Энергия: электрические машины — сумма МВт (с drain); топливные — уголь/мин (energy_usage / fuel_value × effectivity); паровая электростанция под нагрузку (помпа : бойлер : двигатель = 1 : 20 : 40 из прототипов).
- Логистика: предметов/с по каждому потоку → число лент (жёлтая 15/с, красная 30/с …).
- Выбор рецепта при альтернативах: по умолчанию «основной» (main_product, не скрытый, без побочных продуктов); нефть — линейная задача: продукты НПЗ (тяжёлая/лёгкая нефть, газ) и крекинг балансируются решением системы (небольшой симплекс без внешних зависимостей). Basic → advanced oil processing по доступности.
- Ручной крафт: «сколько сырья и секунд руками на N предметов» — для бутстрапа (стадия 7).

**4.4. Путь по технологиям** (`knowledge.TechPath(цель)`)
- Цель: технология / рецепт / предмет / постройка → минимальный набор неизученных тех с предками, в порядке зависимостей (топосортировка).
- Цена: научные пакеты каждого вида × количество, время исследования (unit_time × count / скорость лабораторий); trigger-техи — отдельный список «что сделать руками».
- Какие научные пакеты нужны → их производство через калькулятор.

**4.5. CLI** (`bin/bot calc ...` — работает и без игры, по кэшу `data/`)
- `bot calc ITEM RATE[/s|/min] [ITEM RATE ...] [-machine assembling-machine-2] [-all]` — дерево производства: рецепт, машины (шт. дробно/целых), входы/выходы по каждому узлу; итог: сырьё/мин, буры, печи, МВт и паровая станция, ленты, список нужных исследований. `-all` — как будто всё изучено.
- `bot tech ЦЕЛЬ` — путь исследований: порядок, цена в пакетах, trigger-действия.
- `bot raw ITEM N` — сырьё и время на ручной крафт.
- `-json` для машинной обработки планировщиком.

**4.6. Тесты**
- Юнит (`internal/calc`, `internal/knowledge`) на снимке справочника `testdata/prototypes-2.0.77.json` (в git), сверка с известными числами 2.0:
  - шестерня 60/мин в assembler-1 (скорость 0.5) = 1 машина, 120 железных пластин/мин;
  - электросхема 60/мин → 180 медного провода/мин → 90 крафтов провода, 90 меди + 60 железа;
  - красная наука 1/с в assembler-2 (0.75): 5 с → 6.67 машин; каменная печь — 18.75 пластин/мин; электробур на железе — 0.5 руды/с; пар: 1 помпа : 20 бойлеров : 40 двигателей;
  - нефть: решение баланса НПЗ+крекинг даёт неотрицательные скорости и нулевые излишки;
  - путь к `rocket-silo` включает все его предпосылки, топологически упорядочен, без изученных; `automation-science-pack` — trigger «скрафтить лабораторию».
- e2e (`stage4_test.go`): справочник из живой игры совпадает со снимком (версия игры та же); «доступно сейчас» совпадает с `get_force`; `bot calc rocket-part 1/min` отрабатывает без ошибок и содержит сырьё (руды, нефть, вода) и исследование `rocket-silo`.

**Вне стадии:** модули и маяки (позже), раскладка (стадия 6), исполнение (стадия 5).

Сделано: `knowledge` (граф, Availability, BestCrafter/BestDrill/BestBelt, TechPath, Cost), `calc` (двухфазный симплекс, Solve, Handcraft). Если у предмета нет доступного рецепта или машины — берётся закрытый, а в план добавляются исследования (не «предмет без рецепта»). Насос нефти — номинал 10/с при 100% (реальный дебит скважин меньше). Пар/энергия по соотношениям прототипов; drain учитывается на целые машины.

**Готово, когда:** `bot calc rocket-part 1/min` выдаёт полное дерево производства, сырьё, энергию и список нужных исследований; юнит-тесты сходятся с эталонными числами.

### Стадия 5. Планировщик и стек действий — ✅ готово
Мозг поверх рук (стадия 3) и знаний (стадия 4): цели → дерево задач (HTN) → стек примитивов → исполнение с проверкой и перепланированием. Новые пакеты: `internal/state` (что бот знает о себе и мире), `internal/plan` (цели, задачи, методы, планировщик), `internal/exec` (исполнитель и главный цикл).

**5.1. Состояние (`internal/state`)**
- Снимок, собираемый каждый цикл: игрок (позиция, инвентарь, рука, очередь крафта), сила (изученное), модель мира `world.World` (Sync по событиям), справочник.
- Реестр своих построек: что бот поставил и зачем (unit_number, имя, позиция, «роль»: «печь линии железа №3»). Обновляется по событиям built/mined/died — так видно, что печь кто-то убрал.
- Ресурсы «в доступе»: инвентарь + содержимое своих сундуков и выходов печей (их можно забрать).
- Оценки времени: дорога (длина пути A*), добыча (mining_time, количество), крафт (energy), плавка — чтобы выбирать дешёвый метод.

**5.2. Цели (декларативные, проверяемые по состоянию)**
- `HaveItem(item, n)` — в инвентаре не меньше n.
- `Placed(entity, где, роль)` — постройка стоит (позиция или «рядом с патчем X»).
- `Supplied(постройка, item, n)` — в постройке не меньше n (топливо, сырьё).
- `SmeltingLine(ore, n, fuel)` — n печей у патча руды, у каждой топливо и руда, статус «работает»; составная, поддерживаемая (держится, пока цель активна).
- (позже) `Researched(tech)` — стадия 7 (нужны лаборатории и GUI исследований), `HaveProduction(item, rate)` и `HavePower(MW)` — стадии 6–8 с layout и калькулятором.
- У цели: приоритет, причина (кто её поставил), признак «поддерживать» (после выполнения следить и чинить).

**5.3. Задачи и методы (HTN)**
- Примитивы — обёртки над `act.Hands`: `Walk`, `Gather(target, n)`, `Craft(recipe, n)`, `Place(item, pos, dir)`, `Insert(entity, item, n)` / `InsertAll`, `Take(entity)`, `Pickup(entity)`, `Wait(условие, таймаут)`. У каждого: предусловия, ожидаемый эффект, оценка времени.
- Составные задачи с методами по возрастанию цены:
  - `HaveItem(item, n)`: (1) уже есть → ничего; (2) забрать из своих сундуков / выхода печей; (3) скрафтить руками — рекурсивно `HaveItem` ингредиентов (раскладка из `calc.Handcraft`); (4) добыть с карты (руда, дерево, камень — `Gather`); (5) переплавить: нужна своя печь с топливом → положить руду и уголь → подождать → забрать.
  - `Placed(entity…)`: `HaveItem(предмет)` → выбрать место (простое правило стадии 5: `FreeSpot` у края патча, ряд печей; полноценная раскладка — стадия 6) → `Place`.
  - `Supplied(e, item, n)`: `HaveItem(item, недостача)` → `Insert`.
  - `SmeltingLine`: для каждой печи — `Placed` + `Supplied(уголь)` + `Supplied(руда)`.
- Выбор метода — по оценке времени из состояния (например, плавить в своей печи дешевле, чем копать руду заново, если пластин не хватает на крафт).
- Защита от бесконечной рекурсии: глубина, «уже в обработке» для одинаковых целей, бюджет шагов на план.

**5.4. Планировщик и стек**
- Декомпозиция цели в дерево задач до примитивов; исполнение — стек (верхняя задача — текущая). Каждая задача помнит причину — строка «почему»: «добываю камень → для каменной печи №4 → для линии плавки железа».
- Перед каждым примитивом — проверка предусловий по свежему состоянию (вдруг уже не нужно / изменилось); после — проверка эффекта.
- Перепланирование:
  - примитив упал (нет пути, место занято, курсор не навёлся, не хватает предмета) → откат до ближайшей составной задачи, у которой есть другой метод или другая цель (другое дерево, другое место); метод, упавший N раз, банится на время;
  - цель выполнилась раньше (кто-то положил предмет) → ветка снимается;
  - поддерживаемая цель нарушилась (печь убрали, кончился уголь) → задача ремонта наверх стека;
  - периодический пересчёт целей (раз в N секунд и после каждого примитива — дёшево, по событиям).
- Приоритеты: аварийные (ремонт поддерживаемых целей) > блокирующие текущую > развитие; текущая задача прерывается только на границе примитива.
- Бюджеты и лимиты: максимум попыток на задачу, общее время цели, общий таймаут — бот не зацикливается (уроки стадии 3).

**5.5. Исполнитель и главный цикл (`internal/exec`, `bot run`)**
- Цикл: Sync состояния → проверка целей → (пере)план → один примитив → запись в лог → повтор. Ctrl+C / `-t` — чистая остановка (отпустить ввод, сохранить состояние).
- Перед каждым примитивом — `Say` в консоль игры с причиной («[bot] добываю камень ×10 — для каменной печи №4»).
- Состояние планировщика (цели, реестр построек, баны методов) — в `run/state.json`; при запуске бот продолжает с того же места.
- Лог решений `run/bot.log`: время, цель, выбранный метод и почему, результат примитива, перепланирования.
- Подготовка к тестам — `InsertAll(сундук, предмет)` (Ctrl+ЛКМ с предметом в руке — всё этого вида), чтобы честно «опустошить» инвентарь в сундук.

**5.6. CLI**
- `bot plan ЦЕЛЬ…` — построить план без исполнения: дерево задач с оценкой времени.
- `bot run ЦЕЛЬ… [-t]` — выполнять; цели: `have ITEM N`, `place ENTITY near PATCH`, `smelt ORE N` (линия плавки), `keep` — продолжить сохранённые.
- `bot goals` — текущие цели, их статус и причины.

**5.7. Тесты**
- Юнит (`internal/plan`) на симуляторе: состояние + эффекты примитивов без игры.
  - `HaveItem(stone-furnace, 5)` с пустого инвентаря → план: добыть камень 25 → крафт ×5; с камнем в инвентаре — сразу крафт.
  - `HaveItem(iron-gear-wheel, 10)` без пластин, с печью и углём → плавка, а не «ничего не выходит».
  - Отказ примитива (путь не найден) → другой метод/другая цель; N отказов → бан, без бесконечного цикла.
  - Цель выполнилась извне посреди плана → лишние шаги не исполняются.
  - Нет рекурсии: цикл в рецептах / недостижимая цель → ошибка с объяснением за ограниченное число шагов.
- e2e (`stage5_test.go`):
  - `HaveItem` нескольких предметов, требующих добычи, плавки и крафта.
  - Критерий: инвентарь переложен в сундук → `SmeltingLine(iron-ore, 5, coal)` выполняется сама: 5 каменных печей у железного патча, в каждой уголь и руда, статус «работает».
  - Восстановление: пока цель поддерживается, тест (как «игрок») убирает одну печь → бот замечает и ставит новую; убирает уголь → докладывает.
  - Рестарт: бот остановлен посреди плана → новый запуск продолжает по `run/state.json`.
  - В консоли игры и в `run/bot.log` — причины действий.

**Вне стадии:** раскладка модулей, ленты и роутинг (стадия 6), исследования через GUI и автоматизация (стадия 7), мониторинг дефицитов по статистике (стадия 11).

Добыча бурами (после стадии 5, по решению пользователя): много руды (≥20) — бур на руде + сундук на выходе, персонаж забирает и подкидывает уголь (уголь — с угольного бура); линия плавки держит буры на угле и руде. Линия с нуля ~13 мин (бур 0.25/с вдвое медленнее рук), восстановление ~30 с.

Сделано: планировщик реактивный — на каждом шаге цель заново раскладывается от текущего состояния до одного примитива (план не устаревает; полный план — тот же разбор на симуляторе). Линия плавки: 5 печей с пустого инвентаря ~5 мин, восстановление убранной печи ~1 мин (новым процессом из `run/state.json`). Попутно: прорубание пути сквозь деревья, если персонаж в «кармане»; действия не ходят, если цель уже в досягаемости; Z — докладывание потерянных нажатий.

**Готово, когда:** цель «иметь 5 каменных печей на железе с углём» бот выполняет сам, начиная с пустого инвентаря, и восстанавливается, если ему вручную удалить печь.

### Стадия 6. Layout-движок (где и как строить) — ✅ готово
«На бумаге»: бот раскладывает постройки на модели карты (без строительства — оно в стадии 7) и рисует PNG. Новый пакет `internal/layout`.

**6.1. Сетка и размещение**
- `Placement`: сущность, центр, направление, рецепт; рамка/тайлы по прототипу с поворотом (2.0: 0/4/8/12; восток/запад — ширина ↔ высота).
- `Layout`: список размещений + занятые тайлы; `Grid` — открытая карта (вода, край, утёсы, объекты — не строить; деревья и камни — «можно, но надо срубить», список расчистки) + уже размещённое + зарезервированное.
- Правила тайла: суша; бур — над рудой своего ресурса; помпа — на кромке воды; прочее — не на руде, если можно (не перекрывать месторождения).
- `Validate`: нет пересечений, все тайлы допустимы, ленты непрерывны (каждая лента ведёт в ленту/подземку/вход), инсертеры берут и кладут туда, куда нужно, буры над рудой, столбы покрывают все электрические машины и связаны.

**6.2. Геометрия машин** (из прототипов, с поворотом): выход бура (`vector_to_place_result`), точки инсертера (берёт ↔ кладёт: «север» = берёт сверху, кладёт вниз), зона добычи бура (радиус), покрытие и длина провода столба, дальность подземной ленты.

**6.3. Шахта по форме месторождения** (`Mine(patch, drill, n?)`)
- Не шаблон: колонны лент через месторождение (вертикально или горизонтально — по форме), по обе стороны пары буров, выходом на ленту; бур ставится, только если в его зоне есть руда, а площадка свободна.
- Ленты колонн сводятся в одну выходную ленту у края месторождения → точка выхода (позиция + направление).
- Ранняя игра — burner-буры (без электричества), позже — электрические.

**6.4. Модули-шаблоны** (параметры → размещения + входы/выходы + потребление):
- `SmeltingColumn(n, furnace)` — входная лента (руда + уголь по полосам), инсертеры → печи → инсертеры → выходная лента.
- `AssemblerRow(recipe, n, …)` — сборщики 3×3 с инсертерами вход/выход и лентами; красная наука: шестерни + наука по соотношению калькулятора.
- `SteamPower(engines)` — помпа на кромке воды, бойлер, 2 двигателя.

**6.5. Маршрутизация лент** (`RouteBelt(from, to)`): A* по тайлам, 4 направления, штраф за повороты; подземная лента через препятствие (до дальности прототипа); результат — ленты с направлениями. Деревья на пути — в список расчистки.

**6.6. Электросеть** (`Poles(layout)`): малые столбы — жадное покрытие всех электрических машин зоной столба + связность (провод ≤ 7.5): недостающие столбы цепочкой; соединение с электростанцией.

**6.7. Компоновка** (`Demo`/`Base`): выбрать места модулей — шахта на месторождении, плавильня рядом (не на руде), блок науки рядом, электростанция у воды; связать: шахта → плавильня (руда), уголь → плавильня, плавильня → блок науки (пластины), столбы от станции. Проверка баланса по калькулятору: выход шахты ≥ потребность плавильни ≥ потребность науки.

**6.8. Вывод**
- `world.Render` + наложение раскладки: постройки цветами по типу, ленты со стрелками, столбы, зона расчистки.
- CLI: `bot layout mine РУДА [-o png]`, `bot layout smelt N`, `bot layout science N`, `bot layout demo [-o png]` — печатает размещения, проверки, баланс; без игры — по кэшу и последнему скану недоступно (нужна карта) → требует игру.

**6.9. Тесты**
- Юнит на синтетических картах: повороты и рамки; шахта — все буры над рудой, выходы на ленту, лента непрерывна до точки выхода, нет пересечений; маршрут ленты огибает препятствия и ныряет под стену подземкой; столбы покрывают и связаны; модули валидны; баланс.
- e2e на случайной карте: `demo` строит валидную раскладку без коллизий с объектами карты (по живому скану), PNG создаётся.

**Вне стадии:** строительство раскладки (стадия 7 — бутстрап), main bus и масштабирование (стадия 8), чертежи и роботы (9).

**Готово, когда:** на тестовой карте бот раскладывает (пока «на бумаге» + рисунок PNG) шахту, плавильню и блок красной науки, соединённые лентами, без коллизий.

## 3. Риски

| Риск | Что делаем |
|---|---|
| Промахи кликов / неверная проекция камеры | фиксированные разрешение/UI scale/зум, калибровка по `selected`, проверка каждого действия сенсорами |
| GUI меняется между состояниями (разные окна, поиск) | макросы с подтверждением шагов через `player.opened`, курсор, инвентарь; скриншоты для отладки |
| Скорость: ввод медленнее API | быстрые клавиши (Ctrl+клик, Q, quickbar); роботы как можно раньше |
| Ходьба застревает | A* по карте препятствий + детект застревания + расчистка |
| Большие дампы не лезут в RCON | пагинация или `helpers.write_file` в `script-output` сервера и чтение файла |
| Мод случайно меняет состояние игры | в remote interface только чтение; бот не шлёт произвольных `/c` |
| Раскладка лент — самое сложное | жёсткие шаблоны + простой A*, усложняем по необходимости |
| Бот «тупит» в цикле перепланирования | лимиты попыток, бан метода после N неудач, лог причин |
| Xephyr + OpenGL медленный | `-glamor`; fallback — отдельный X-экран или окно на основном дисплее (тогда мышь занята) |
